# Evidence-based paper repair learning

Jarvis keeps a durable lesson for terminal isolated repair runs. It records the exact test stage that did not pass, or independently verified live recovery, together with bounded before/after health aggregates. The next investigation receives up to eight relevant lessons, actual identifier-free chart helper inputs, supporting helper source, and unchanged constants. Provider staleness, quota exhaustion, missing history and zero-volume baselines receive specific next measurements, not invented indicators or claims of strategy failure. Low partial coverage is diagnosed without changing incident confirmation thresholds.

A failed replacement is fingerprinted using its Python syntax tree and exact base source digest. Whitespace and regression-test renaming do not bypass the block. Test failures and rolled-back fixes cannot be automatically repeated against the same source. Runner outages and expired leases get a one-hour cooldown instead of being called code defects. A failed test or rollback makes a follow-up investigation due after five minutes, with at most three investigations per incident and unchanged daily/monthly reservations. Two isolated repair starts per rolling day remain the limit.

The trusted runner now correctly accumulates five consecutive distinct fresh observations spanning at least two minutes. Any unhealthy, duplicate, stale or wrong-commit observation prevents verification. An owner pause cannot establish incident recovery, but can allow a verified rollback. Previously, a boolean assignment reset the counter every poll, making five checks unreachable. Dedicated runner tests cover this path outside the generated-code sandbox; the isolated sandbox still mounts no CI controller or credentials.

Automatic code scope remains the four existing pure paper scheduling/freshness helpers. Generated changes still require a regression that fails on the baseline, passes on the candidate, the existing Solana suite in an isolated container, independent live recovery, and rollback on failed verification. Changes to accounting, real-money trading, credentials, budgets, validation gates, tests and the repair controller remain outside model authority. Lessons appear on System investigations under Repair memory. No laptop update is needed.
